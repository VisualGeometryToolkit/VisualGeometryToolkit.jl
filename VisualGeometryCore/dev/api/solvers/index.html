Solvers API

Projective solver kernels (homography, fundamental, essential, P3P), slot-labeled epipolar forms, model-validity tests, and the zero-allocation SVD workspace, and the total-least-squares line. The solve protocol and the solver registry are documented with the Correspondence API; see the Epipolar Forms guide.

Normalization

One scheme serves every solver. A normalization STRATEGY is a type named <Method>Normalization, applied as a coordinate map with AffineMap(strategy, points[, mask, weights]):

  • HartleyNormalization(; center) — translate to the (weighted) centroid, or to a known center, and scale to mean distance √2. Estimation uses it: the centroid for H, F and E; the known distortion centre for the radial models, whose solvers are written about the origin.
  • DiagonalNormalization(size; center) — the image centre and the half-diagonal (corners at unit radius, NormalizedImageFrame coordinates). For storage only: the benchmark pools, where one noise level and one threshold must mean the same across resolutions.

A correspondence set's normalization is one value, CspondNormalization: both sides' maps and their inverses, built from two strategies or by model type (CspondNormalization(M, cs; center)), with normalize and the side accessors, whose composition moves a model (D ∘ M ∘ inv(S) into the normalized frame, inv(D) ∘ M ∘ S back). An estimator normalizes once at its entry and returns results in its inputs' frame; the DLT kernels take the enclosing normalization as normalization.

Epipolar Forms

VisualGeometryCore.EpipolarForm — Type
EpipolarForm{S1<:Frame{2}, S2<:Frame{2}, M<:AbstractFundMat}

Slot-labeled epipolar form: a bilinear form with two contravariant point arguments, wrapping a frame-free FundMat or EssentialMat.

Slot convention (pinned here; every other method defers to this): slot 1 takes points of frame S1 (view 1), slot 2 takes points of frame S2 (view 2), and the wrapped matrix M satisfies

x₂ᵀ M x₁ = 0

for corresponding x₁ ∈ S1, x₂ ∈ S2 (homogeneous). Slot 1 is the RIGHT argument of the matrix, matching the u₂ᵀ F u₁ convention used throughout the solver layer. In slot-monogram terms the form is M_{S2,S1} — first index left slot, second index right slot.

The frame tags label the slots of a form, not the endpoints of a map: an EpipolarForm is not a Transformation, does not compose with ∘, and has no inv (deliberately — see the note below). Its point ↦ line action is epipolar_map, and a frame change is composition on that map: EpipolarForm(H₂ ∘ epipolar_map(f) ∘ inv(H₁)) (see ∘ on EpipolarMap).

Construction is the labeled Mat → form lift; unlabeled lifts are allowed for gradual adoption (both slots UnlabeledFrame{2}):

form = EpipolarForm{ImageFrame{:a}, ImageFrame{:b}}(F)   # labeled lift
form = EpipolarForm(F)                                 # unlabeled lift

Evaluating the form applies the slot convention operationally: form(x₁, x₂) returns the scalar x̃₂ᵀ M x̃₁ (zero for an exact correspondence). The wrapper does NOT enforce the rank-2 (or E-manifold) constraint — that discipline belongs to the wrapped Mat type and the solvers that produce it.

Why there is no inv

The epipolar correlation is rank 2: its kernel is the epipole e₁ (M e₁ = 0), every point on one epipolar line maps to the SAME line in the other view, and the image is not all lines but the 1-parameter pencil through the other epipole e₂. A 2-parameter point domain collapsing onto a 1-parameter family of lines has no inverse — inv(::EpipolarForm) is deliberately left undefined (a MethodError), and transpose (swap the slots) is the only involution the form supports. Use epipoles to make the degeneracy explicit.

See also epipolar_map, EpipolarMap, epipoles, sampson_distance, ImageFrame.

VisualGeometryCore.HomographyMap — Method
HomographyMap(f::TransferForm{Src, Dst}) -> HomographyMap{Src, Dst}
TransferForm(h::HomographyMap{3, T, M, Src, Dst}) -> TransferForm{Src, Dst}

A transfer form's tags are endpoints, so its homography IS a framed HomographyMap with the same two frames, and its frame change is that map's composition (frame-checked by the map's own junction rule): with D₁, D₂ carrying the current endpoints into the new ones,

TransferForm(D₂ ∘ HomographyMap(f) ∘ inv(D₁))   has   H′ = D₂ · H · D₁⁻¹.

An estimator that solves in a model frame holds MEASUREMENT maps Cᵢ carrying data-frame points into the model frame (x̃ᵢ = Cᵢ xᵢ; for calibrated homography Cᵢ = Kᵢ⁻¹), so moving the solved model back to the data frame is inv(C₂) ∘ HomographyMap(f) ∘ C₁. inv on a HomographyMap is an O(1) swap of its two stored matrices.

A residual is EQUIVARIANT, not invariant: g = π(H x̃₁) − x₂ is a displacement in the destination image, so a frame change moves it by that frame's local Jacobian — exactly (not to first order) for an affine D₂, whose Jacobian is constant. What IS frame-independent is the ZERO SET (an exact correspondence stays exact in every frame). Measured over 2000 random draws with κ(H), κ(D₁), κ(D₂) ≤ 100 (pinned, seed and all, in test/transfer_composition_tests.jl), as a relative error against max(|value|, 1):

VisualGeometryCore.compose_jacobian — Method
compose_jacobian(outer, m, inner) -> SMatrix{9, 9}

The derivative of the composition outer ∘ m ∘ inner in the model's matrix, ∂vec(M′)/∂vec(M) (column-major vec), for m an EpipolarMap or a HomographyMap{3} and outer/inner collineations (a HomographyMap{3} or a CoordinateTransformations affine). The composition is linear in M, so this is the constant Kronecker factor of its law (_conjugation_jacobian, the one ∂vec(A·M·B)/∂vec(M)), B = inner's matrix and A = outer's:

  • correlation, M′ = A⁻ᵀ·M·B: kron(Bᵀ, A⁻ᵀ);
  • collineation, H′ = A·H·B: kron(Bᵀ, A).

What a constraint evaluated on the composed model needs to pull its model gradient back into the model's own coordinates: ∂g/∂vec(M) = Jᵀ·∂g/∂vec(M′) for a scalar constraint's 9-vector, G_θ·J for a 2×9. Frame-checked like ∘; in the promoted element type of the model and the maps.

VisualGeometryCore.constraint_with_jacobians — Method
constraint_with_jacobians(f::TransferForm, u₁, u₂) -> (g, G_x, G_θ)

The transfer constraint of the wrapped homography and its Jacobians: g = π(H·ũ₁) − u₂, the transfer error in the destination image, with G_x = [Jπ·H₁₂ −I₂] (2×4, over (x₁, y₁, x₂, y₂)) and G_θ = Jπ·(ũ₁ᵀ ⊗ I₃) (2×9, ∂g/∂vec(H) column-major), Jπ the perspective derivative at H·ũ₁ and H₁₂ the first two columns of H.

The ALGEBRAIC counterpart is constraint_with_jacobians(H, u₁, u₂) on the bare Mat — same verb, same return shape, different residual. Which one you get is decided by whether the model is wrapped in a TransferForm, not by a second function name. Generic in the element type; device-safe. Image points only: u₁, u₂ are 2-vectors, and a 3-vector (a bearing) is a MethodError.

VisualGeometryCore.epipolar_map — Method
epipolar_map(f::EpipolarForm{S1, S2}) -> EpipolarMap{S1, S2}

The honest epipolar correlation: a callable taking a point x₁ in slot 1's frame S1 and returning its epipolar LINE in slot 2's frame S2,

ℓ₂ = M x̃₁

as a Line2D — VGC's 2D Hyperplane, i.e. the covector of the incidence constraint ℓ₂ᵀ x̃₂ = 0. The returned line is itself a one-slot form (a linear form on S2-frame points), which is why a correlation lands on Line2D and not on a point type: point ↦ line, not point ↦ point.

epipolar_map(transpose(f)) goes the other way (S2 points to S1 lines, via Mᵀ). There is no inverse map — the correlation is rank 2 (see EpipolarForm); the two degenerate directions are exposed by epipoles.

Note

Since 0.8 this name refers ONLY to the form action. The former epipolar_map(source::Camera, target::Camera, extrinsics) — a unit-depth point-TRANSFER closure, not an epipolar correlation — is renamed depth_transfer.

VisualGeometryCore.epipoles — Method
epipoles(f::EpipolarForm{S1, S2}) -> (e₁, e₂)

The two kernels of the rank-2 form, labeled by their frames: e₁ is the epipole in slot 1's frame S1 (right kernel, M e₁ ≈ 0) and e₂ the epipole in slot 2's frame S2 (left kernel, Mᵀ e₂ ≈ 0), returned as a NamedTuple (e₁ = ..., e₂ = ...) of homogeneous SVector{3} (unit norm, from the SVD null vectors — homogeneous because an epipole can lie at infinity; dehomogenize with to_euclidean when e[3] ≠ 0).

These are the degenerate directions that make the correlation one-way: epipolar_map sends e₁ to the zero "line", and every returned line goes through e₂ (the pencil property). Computed by SVD of the wrapped matrix; for a noisy or rank-3 matrix the returned vectors are the nearest-kernel directions.

Base.transpose — Method
transpose(f::EpipolarForm{S1, S2}) -> EpipolarForm{S2, S1}

Swap the slots of the form: wraps Mᵀ, so the constraint reads x₁ᵀ Mᵀ x₂ = 0 — the same incidence relation with the argument order exchanged. An involution (transpose(transpose(f)) recovers f), and the ONLY inversion-like operation the form supports — the rank-2 correlation has no inv (see EpipolarForm). The wrapped Mat type is preserved: the transpose of a fundamental matrix is fundamental, and Eᵀ remains on the essential manifold.

adjoint (f') is the same operation (real coefficients).

VisualGeometryCore.CspondNormalization — Type
CspondNormalization(T_src::AffineMap, T_dst::AffineMap)
CspondNormalization(src::Normalization, dst::Normalization, cs[, mask, weights])
CspondNormalization(M::Type, cs; center)

The normalization of a correspondence set as a first-class value: the forward homogeneous maps of the source and target sides AND their analytic inverses, computed once at construction (never per candidate model). Build it from two affine maps, from a normalization strategy per side (HartleyNormalization, DiagonalNormalization) applied to the correspondences' sources and targets, or by MODEL TYPE — the strategy each model class needs:

  • HomographyMat / AbstractFundMat (F and E): Hartley at the centroid on both sides (the classic DLT data normalization), over the mask's correspondences and weighted by the weights column when there is one;
  • RadialHomography: Hartley at the centroid on the sources, Hartley about the known distortion center (required) on the targets — the origin the 5-point kernel is written about.

Verbs:

  • normalize(normalization, cs) — materialized normalized correspondence set
  • source_map / target_map — its two sides as affine maps
  • a model moves by composition with the two sides: target_map(N) ∘ M ∘ inv(source_map(N)) carries a data-frame model M into the normalized frame and inv(target_map(N)) ∘ M ∘ source_map(N) back (M a HomographyMat, a FundMat/EssentialMat, a HomographyMap, an EpipolarMap, a RadialHomography, a RadialCamera).

The pose family builds none (bearings are already metric).

VisualGeometryCore.HartleyNormalization — Type
HartleyNormalization(; center = nothing)

Hartley's data normalization as a STRATEGY (Hartley & Zisserman §4.4): translate to the (weighted) centroid of the points — or to a KNOWN center — and scale isotropically so that the mean distance from it is √2. Apply it with AffineMap(HartleyNormalization(...), points[, mask, weights]).

VisualGeometryCore.homography_4pt — Method
homography_4pt(s₁, s₂, s₃, s₄, d₁, d₂, d₃, d₄) -> SMatrix{3,3} or nothing

Compute a homography from exactly 4 point correspondences using the inhomogeneous method (two 3×3 LU solves, zero heap allocation).

Returns a Frobenius-normalized SMatrix{3,3} with H[3,3] >= 0, or nothing if the points are degenerate (collinear).

Algorithm

From "An Algebraic Derivation of the Inhomogeneous Homography":

  1. Build U3 = [u1|u2|u3], solve U3*c = -u4 for projective depths
  2. Build U3' = [u1'|u2'|u3'], solve U3'*c' = -u4' for target depths
  3. λi = c'i / c_i (projective depth ratios)
  4. H = U3' * diag(λ) * inv(U3)

Example

s = [SA[0.0,0.0], SA[1.0,0.0], SA[1.0,1.0], SA[0.0,1.0]]
d = [SA[0.1,0.1], SA[1.1,0.0], SA[1.0,1.1], SA[0.0,1.0]]
H = homography_4pt(s[1], s[2], s[3], s[4], d[1], d[2], d[3], d[4])

VisualGeometryCore.homography_dlt! — Method
homography_dlt!(A, N::CspondNormalization, cs; mask = nothing, svd_ws = nothing) -> HomographyMat or nothing

In-place N-point DLT of the correspondences cs using the pre-allocated buffer A (2N × 9). Weights are the container's weights column, as for homography_dlt; inside an LO/IRLS loop set them per iteration with withattrs(cs; weights = w) (no allocation beyond the caller's w).

When mask::BitVector is provided, only masked points are used and rows are compacted into the top of A. The inner-loop form: N is the enclosing estimator's CspondNormalization, built once at its entry (the public form builds it from the data); this form applies it row by row and composes the model back into the data frame (inv(D) ∘ H ∘ S), and never normalizes on its own.

If svd_ws::SvdWorkspace is provided and A is Float64, uses pre-allocated LAPACK workspace for the SVD (zero allocations). Note: A is overwritten when using svd_ws.

No covariance is returned. The DLT minimizes ALGEBRAIC residuals, whose noise is heteroscedastic under pixel noise, so the SVD's own resolvent covariance is not this estimator's (measured overconfident against Monte Carlo). Its first-order covariance, if ever needed, is implicit_covariance's block form with the DLT's identity weighting.

VisualGeometryCore.is_orientation_preserving — Method
is_orientation_preserving(h::HomographyMap{3}, rect::HyperRectangle{2}) -> Bool

True iff the four corners of rect map through h to a simple (non-self-intersecting) convex quadrilateral. Catches "bow-tie" homographies that the per-correspondence checks (test_cheirality, test_conditioning) miss — these come from H fits that are well-behaved over the inlier cluster but extrapolate to fold the rectangle's corners across each other.

VisualGeometryCore.test_cheirality — Method
test_cheirality(H, cs, idx) -> Bool

Projective cheirality check, uniform-sign variant. For each correspondence (uᵢ, u′ᵢ) at the sample indices, compute the projective scale factor λᵢ such that ũ′ᵢ = λᵢ · H · ũᵢ in homogeneous coordinates, where ũ = [u; 1]. Accept iff all λᵢ share a sign.

Rationale — H is only defined up to a nonzero scalar (H and −H are the same mapping). Under H → −H, every λᵢ flips sign, so requiring a specific sign (e.g. the original Shekhovtsov rule: sign-normalize to det(H) > 0, then require λ > 0) amounts to picking a matrix representative by convention. That convention matches the image-to-image case (where both frames share 2D handedness) but fails for object-to-image homographies (e.g. a world y-up calibration board mapped to a y-down image), where the "in front" representative has det(H) < 0 — the strict rule then rejects every correct fit.

The mapping-level invariant is uniform sign across the λᵢ: mixed signs signal a bow-tie in projective depth (a real pathology that cannot be repaired by a matrix sign flip), while a shared sign — positive or negative — signals a consistent mapping (with the overall sign absorbed into the free scalar of H).

For each i: compute Hu = H · ũᵢ, pick the component k with the largest absolute value (numerical robustness), and set λᵢ = ũ′ᵢ[k] / Hu[k] (with ũ′[3] = 1). Reject the sample the moment a sign disagreement is seen. An inner-loop gate: H and cs in the same frame (sign-based, so any positive-scale normalization, or none, gives the same answer).

VisualGeometryCore.test_conditioning — Method
test_conditioning(H; max_cond=100) -> Bool

Reject homographies whose SVD condition number κ = σ₁/σ₃ exceeds max_cond.

Catches near-rank-deficient H — the same pathology PoseLib's post-solve |det(H_normalized)| < 1e-8 check rejects (since after Frobenius normalization det(H) = σ₁σ₂σ₃ and one vanishing singular value makes both κ → ∞ and det → 0), plus a broader class of numerically unstable but non-singular H's.

Matches Shekhovtsov's is_homography_ill_conditioned (decompose_homography.py:244) with the same default threshold κ = 100.

κ is a property of the frame H is written in, not of the map: the bound is calibrated for H between Hartley-normalized frames (both sides, as CspondNormalization builds them), so evaluate it on the normalized H, never on a pixel-frame one.

VisualGeometryCore.test_model — Method
test_model(F::FundMat, u₁_sample, u₂_sample) -> Bool

Oriented epipolar constraint (Chum et al. 2004). For an exact correspondence, the epipolar line l₁ = Fᵀũ₂ and the line e₁ × ũ₁ are the same line in image 1 (both go through e₁ and ũ₁), so Fᵀũ₂ = μᵢ(e₁ × ũ₁) for some scalar μᵢ. The signum uses the dot product of all three components:

sᵢ = (Fᵀũ₂ⁱ) · (e₁ × ũ₁ⁱ) = μᵢ · ‖e₁ × ũ₁ⁱ‖²

Since ‖e₁ × ũ₁ⁱ‖² ≥ 0, sign(sᵢ) = sign(μᵢ). The code checks sᵢ · sⱼ > 0 for all pairs, i.e., that all μᵢ share the same sign. Using the full dot product (rather than a single component) avoids numerical instability when one component happens to be near zero.

This is a chirality parity check. The absolute sign of μᵢ is meaningless (F and e₁ are projective, defined up to scale), but if two correspondences give different signs, they cannot both be in front of both cameras. The test rejects F matrices that are algebraically valid (u₂ᵀFu₁ = 0) but geometrically inconsistent. An inner-loop gate: F and the points in the same frame, the estimator's normalization (sign-based, so any positive-scale normalization gives the same answer).

VisualGeometryCore.triangulate — Method
triangulate(pose::EuclideanMap{3}, f₁, f₂) -> (X, λ₁, λ₂)

Triangulate a correspondence of UNIT BEARINGS: the midpoint of the mutual perpendicular between the two rays, in VIEW 1's frame, together with both ray depths. pose maps view 1 to view 2 (X₂ = R·X₁ + t).

The depths are the point of returning them. Cheirality on rays is `λ₁ > 0 && λ₂

0` — the point is in front of both cameras along their own rays — which is

the plane-free replacement for testing X[3] > 0. A z-depth test silently assumes a forward hemisphere the ray domain does not have, so it is wrong for any camera that sees past 90°.

Returns λ₁ = λ₂ = NaN for parallel rays (|f₁·R'f₂| → 1), which is degenerate rather than exceptional: it is what zero parallax looks like, and the caller decides. Never throws.

Why this form, and what it costs

It is the only form that GENERALISES. The pixel-domain DLT (uᵢ × Pᵢ X̃ = 0) builds P = K[I|0] — pinhole by construction — and calibrated geometry in this stack must work for fisheye and omnidirectional cameras, where that matrix does not exist. That is the deciding argument, and it is not a number.

MEASURED against that DLT rather than assumed better, paired (identical scenes, points and noise draws), binned by parallax, on relative 3-D error. Reprojection error cannot discriminate the two — it sits at the noise level even where the 3-D error reaches 363 — so it is reported only as a sanity check. The trade is real and mixed:

apex anglemed DLT → rayq99 DLT → rayray wins (paired)
[0, 0.1°)0.488 → 0.56721.9 → 1.7343.3%
[0.1, 0.3°)0.170 → 0.1743.69 → 1.3845.4%
[0.3, 1°)0.0592 → 0.05850.354 → 0.33648.0%
[1, 3°)0.0202 → 0.02010.092 → 0.092547.8%
[3, 90°)0.00597 → 0.005950.0279 → 0.027947.6%

So: it WINS ONLY IN THE TAIL, and decisively there — a q99 of 21.9 is a point placed at 22× its true distance, and those are what corrupt a bundle or a cheirality vote downstream. It is slightly WORSE on the median below 0.1° (43.3% of paired points, i.e. it loses more often than it wins), in a regime where both answers are already about half the true distance. Above 0.3° the two are indistinguishable to three significant figures. Noise-free both are exact to 1e-13–1e-16, so the entire difference is noise propagation near degeneracy, not conditioning.

A NEGATIVE RESULT worth keeping: ray-depth cheirality does NOT reduce the behind-camera rate. Below 0.1° parallax it is 20.1% for the DLT's z-test and 20.4% here; in [0.1, 0.3°) both are 0.23%. That was predicted to improve and measured not to — at that parallax the noisy rays genuinely cross behind a camera, so it is the geometry, not the test. Ray depth is still the right statement (a z-test assumes a forward hemisphere the ray domain lacks), but it buys correctness of MEANING, not accuracy.

VisualGeometryCore.tls_line — Method
tls_line(points) -> Uncertain{Line2D{T}}
tls_line(points, weights) -> Uncertain{Line2D{T}}

Total least squares (orthogonal distance regression) line through points (2-vectors): the centroid, and the scatter matrix's smallest-eigenvalue eigenvector as the normal — one closed-form step. The line is in Hesse form n⊤p + d = 0, n = (cos φ, sin φ), and carries the covariance of θ = (φ, d): s² (JᵀWJ)⁻¹, with s² = Σwᵢrᵢ²/(n₊−2) the residual variance, n₊ the number of points with positive weight and J the residual Jacobian — calibrated against Monte Carlo.

weights are FIXED non-negative per-point weights (wᵢ = 1/σᵢ² for known isotropic variances): the weighted centroid, the weighted scatter, and a zero weight drops the point. Without them every point weighs 1. Throws ArgumentError for fewer than 3 points of positive weight, a negative or non-finite weight, or a weights whose length differs from points'.

For points carrying their own covariances, RobustVisualGeometry's fit_line (an iterative weighted fit) applies.

VisualGeometryCore.tls_line_statistics — Function
tls_line_statistics(points, weights[, normal]) -> (line, S, JᵀWJ)

The weighted total-least-squares line of tls_line(points, weights) with the two statistics its covariance is made of, both at the returned line: the weighted residual sum S = Σwᵢrᵢ² and the (φ, d) information JᵀWJ (J's rows (tᵀpᵢ, 1), t the line's direction). The residual variance is S/(n₊ − 2) and the covariance S/(n₊ − 2)·(JᵀWJ)⁻¹; a caller that owns its own variance model reads the pieces instead.

With normal given (a 2-vector, taken as is), the step estimates the offset only: the line with that normal through the weighted centroid — the least-squares offset for a known normal.

weights as for tls_line: FIXED and non-negative, a zero weight drops the point; there is no minimum count here (the covariance's is the caller's), but weights that sum to zero throw ArgumentError.

VisualGeometryCore.test_dlt_conditioning — Method
test_dlt_conditioning(ws::SvdWorkspace; max_cond = 100.0, null_dim = 1) -> Bool

Is the DLT design matrix of the solve that filled ws well enough conditioned to trust? dlt_conditioning(ws; null_dim) <= max_cond. An inner-loop gate: true succeeds, like every other test_* here.

NOT test_conditioning, and the difference is the point. test_conditioning(H) measures the MODEL matrix; this measures the DESIGN matrix's null-space gap — whether the solution direction is isolated. VisualGeometryCore.test_sample — Method
test_sample(::Type{<:EssentialMat}, cs, idx; tol_px = COINCIDENT_PX) -> Bool

The same coincidence question for E on UNIT BEARINGS: are any two of the sample's bearings the same detection? Bearings are directions, so the comparison cannot be a distance between them — it is the angle, converted to pixels through each point's backprojection Jacobian.

cs carries M₁/M₂ as attribute COLUMNS (withattrs(cs; M₁, M₂)), the 3×2 Jacobians from backproject_with_jacobian; the pair's separation in pixels is estimated as angle(fₐ, f_b) / σ_max(M). Without those columns (any container without them, a plain Pair vector included) this takes the shared bearing-free path of the F method, because there is then no way to convert an angle into the caller's units — and guessing one would be a threshold with nothing behind it.

The estimate is CONSERVATIVE, and by how much

M is generally anisotropic: a pixel step produces a different angle along its major and minor singular directions. Dividing by σ_max therefore UNDER-states the separation of a pair displaced along the minor direction, by exactly the factor 1/aniso (aniso = σ_max/σ_min) — measured to five digits across a fisheye field. Rejection happens when the estimate falls below tol_px, so the gate actually rejects true separations up to tol_px × aniso: the effective threshold is tol_px along M's major axis and tol_px × aniso along its minor.

Larger, not smaller — so it never UNDER-rejects, which is the failure a deduplication backstop must not have. It begins over-rejecting genuinely DISTINCT features only when tol_px × aniso > d_min, i.e. aniso > d_min / tol_px — aniso > 10 for the default 0.1 px and features no closer than 1 px. A moderate KannalaBrandt fisheye (f = 300, k1 = −0.02) reaches aniso 1.48 at field radius 386 px, an effective 0.148 px: about 7× below where distinct features live. Stated because this stack exists for strongly distorted lenses, and a field-varying threshold is otherwise the kind of thing that resurfaces as unexplained behaviour at the periphery.

The tangency contract

M is tangent to its bearing — fᵀM = 0, measured to 4e-20 across the field — which is why no explicit projection onto the tangent plane appears here or in any consumer. It is a CONTRACT, not an observation: a violation would show up as slow drift rather than an error, so it is pinned at backproject_with_jacobian and depended on here.

VisualGeometryCore.dlt_conditioning — Method
dlt_conditioning(ws::SvdWorkspace; null_dim::Int = 1) -> Float64

The DLT design matrix's null-space gap from the solve that filled ws: S[1] / max(S[n - null_dim], eps()), the largest singular value over the smallest NON-null one (n = length(ws.S); for the 9-column homography and fundamental systems, S[1]/S[8]). The eps() floor is load-bearing: an exactly rank-deficient design matrix returns an enormous ratio rather than dividing by zero, which is how a collinear correspondence set announces itself.

A MEASUREMENT, not a policy: it neither rejects nor alters the solve. Pair it with test_dlt_conditioning, whose default 100.0 is the one threshold: RobustVisualGeometry's refine!(::DltWorkspace, …) refuses a relative-family hypothesis by calling it at that default.

ONLY MEANINGFUL IN THE COORDINATES THE SOLVE USED. The ratio is a property of the design matrix as built, so it depends on the normalization AND on the weights column that went into it. VGC's public DLT forms build a HartleyNormalization, which is what makes a threshold of 100.0 mean the same thing here as in RobustVisualGeometry — a caller that solves in another frame must recalibrate its threshold rather than carry this one across.

REFLECTS THE LAST SOLVE that filled this workspace, and nothing checks that for you: read it immediately after the homography_dlt!/fundamental_dlt! call whose matrix you mean. There is deliberately no staleness flag — adding one means a field on SvdWorkspace, which RobustVisualGeometry constructs too, so it would turn a local guard into a cross-repo API change and a lockstep window, to protect against a mistake this sentence prevents.
