Transforms API

Framed maps — the geometric objects, whose type is their transform class — the dense homography matrix, coordinate conversions, uncertainty propagation, and the SO(3)/SE(3) helpers. Region maps and image warping are on the Warping API page. See the Transforms and Coordinate Frames guides.

Framed Maps

A map acts on a primitive in its class: an EuclideanMap or a SimilarityMap keeps a circle a Circle (and a feature frame its type), an AffineMap gives a HomEllipseMat, a HomographyMap a Conic (the actions are on the Warping API page).

VisualGeometryToolkitCore.CameraPose — Type
CameraPose

Frame-pair alias for a camera POSE (camera-to-world transform): CameraPose{T, R, V} = EuclideanMap{3, T, R, V, CameraFrame, WorldFrame} (monogram X_WC). Not a wrapper — a CameraPose IS an EuclideanMap, so .R/.t, point application, and composition all apply directly.

The typed algebra subsumes the former wrapper machinery: inv(::CameraPose) -> CameraExtrinsics (and back) via the frame swap, and PosedCamera(model, ::CameraPose) inverts internally into the extrinsics slot, so handing a pose where extrinsics are expected is unrepresentable.

VisualGeometryToolkitCore.EuclideanMap — Type
EuclideanMap{N,T,R<:Rotation{N,T},V<:StaticVector{N},Src<:Frame{N},Dst<:Frame{N}} <: Transformation

Rigid transformation x ↦ R*x + t in N dimensions, combining rotation and translation.

This represents a Euclidean (rigid body) transformation that preserves distances and angles. It consists of a rotation R followed by a translation t.

The translation's element type is free. A PHYSICAL map — a camera or target pose, a rig member — holds FlexUnits' base-form quantities, Quantity{T, Dimensions{FixRat32}} in metres (UnitfulEuclideanMap); an inner-loop map holds plain numbers — Float64, Float32, a ForwardDiff Dual — beside a rotation of its own eltype T (PlainEuclideanMap). has_units tells them apart, ustrip(u, E) gives the plain map in the unit u, and attaching a unit is construction, EuclideanMap(rotation(E), translation(E) .* u). A unitful map meeting plain numbers — applied to a plain point, composed with a plain map — is FlexUnits' DimensionError, never a promotion.

The trailing Src/Dst parameters are coordinate-Frame tags: the map consumes Src-coordinates and produces Dst-coordinates (Drake monogram: X_AB ≙ Src = B, Dst = A). All constructors that do not state frames produce Src = Dst = UnlabeledFrame{N} — labels are opt-in and never viral. inv swaps the frames; ∘ checks the junction frame between two labeled maps (see the truth table at that method) and throws a MethodError on a labeled mismatch. Use relabel/unlabel as explicit escape hatches.

Fields

  • R::Rotation{N,T}: Rotation component (from Rotations.jl)
  • t::StaticVector{N}: Translation vector — plain numbers, or lengths in metres

Constructors

# From rotation and translation vector
R = RotMatrix{2}(π/4)  # 45° rotation
t = [2.0, 1.0]         # translation
euclidean = EuclideanMap(R, t)

# From MRP (Modified Rodrigues Parameters) for 3D
mrp = MRP(0.1, 0.2, 0.3)
euclidean_3d = EuclideanMap(mrp, [1.0, 2.0, 3.0])

# A physical pose: the translation a length (stored in metres)
pose = EuclideanMap(mrp, SVector(62.8, 0.0, 1200.0) .* mm)

# From tuple
euclidean = EuclideanMap((R, t))

Usage

# Apply transformation to points
point = Point2f(1.0, 0.0)
transformed = euclidean(point)

# Compose transformations
combined = euclidean2 ∘ euclidean1

# Inverse transformation
inverse_euclidean = inv(euclidean)

Construct a rigid-body transform directly from a 3×3 SMatrix (not already a Rotation type). This is the boundary constructor — the entry point at which raw 3×3 numerical data crosses into the typed EuclideanMap. VisualGeometryToolkitCore.angle_between — Method
angle_between(u, v) -> Real

The angle between two vectors of 2 or 3 entries, in radians in [0, π]: θ = atan(‖u × v‖, u · v) (for 2-vectors ‖u × v‖ = |u₁v₂ − u₂v₁|). Neither vector need be unit: the form is scale-free. Accurate at every angle, where the acos of the normalized dot product loses half the digits near 0 and π (its derivative is unbounded there): two unit vectors 1e-8 rad apart have a dot product that rounds to 1, so acos returns 0 (or 1.5e-8 a few ulps away), and this form returns the angle to full precision. 0 when either vector is zero; NaN in, NaN out. Generic in the element type (ForwardDiff duals flow through away from θ = 0, where ‖u × v‖ has no derivative). The angle between two bearings, two rotation axes, a predicted and an observed ray; for two translations up to scale, lengths included, translation_angle.

VisualGeometryToolkitCore.constraint_with_jacobians — Method
constraint_with_jacobians(pose::EuclideanMap{3}, X::SVector{3}, ray::SVector{3})
    -> (g::SVector{2}, G_x::SMatrix{2,5}, G_θ::SMatrix{2,6})

Compute the reprojection constraint and its derivatives for a 3D rigid pose.

The constraint is the perspective-projected residual in calibrated coordinates: g = π(R·X + t) − π(ray)

where π is perspective division [x,y,z] → [x/z, y/z] and ray is the backprojected observation (encodes camera calibration).

The model Jacobian G_θ uses the left-perturbation convention with a 6-DOF parameterization δ = (δω₁, δω₂, δω₃, δt₁, δt₂, δt₃): ∂g/∂δ = Jπ · [−[X_cam]× I₃]

where Jπ is the 2×3 perspective division Jacobian and [v]× is the skew-symmetric (cross-product) matrix of v.

Returns:

  • g::SVector{2,T} — reprojection residual (calibrated coordinates)
  • G_x::SMatrix{2,5,T} — ∂g/∂(X, ray₁, ray₂) measurement Jacobian
  • G_θ::SMatrix{2,6,T} — ∂g/∂(δω, δt) pose perturbation Jacobian
PINHOLE ONLY — this residual lives in the gnomonic chart

π divides by the third component, so this is the z = 1 chart (GnomonicFrame) and it exists only on the forward hemisphere. It is degenerate at 90° from the optical axis and cannot represent a ray with Z ≤ 0 at all. That is correct for a PINHOLE camera and wrong for a fisheye or omnidirectional one, whose rays routinely go past 90°.

It is legitimate where it is used — VisualGeometryToolkitEstimation's Pinhole PnP LM — and must not become the general path. The camera-general route is the ray-domain pixel residual (constraint_with_jacobians(model, pose, X, u) in cameras/camera_models.jl), which projects through the camera's own lens and therefore never assumes the chart exists. Calibrated two-view geometry takes the same view: it acts on unit bearings (unit rays, StaticVector{3}), never on this chart.

VisualGeometryToolkitCore.SimilarityMap — Type
SimilarityMap{N,T,S,R<:Rotation{N,T},V<:StaticVector{N},Src<:Frame{N},Dst<:Frame{N}} <: Transformation

The similarity transformation x ↦ s·R·x + t of N-space: a positive scale s, a rotation R (a Rotations.jl Rotation{N}) and a translation t.

S = SimilarityMap(2.0, RotMatrix{2}(π / 6), SVector(1.0, -3.0))
S(circle)                  # a Circle: centre mapped, radius · 2
S ∘ inv(S)                 # a SimilarityMap (the identity, up to rounding)
SimilarityMap(E)           # an EuclideanMap, s = 1 (also a rotation LinearMap, a Translation, a uniform scaling)

Accessors scale, rotation, translation. ∘ with a similarity, an EuclideanMap or a Translation (either order) is a SimilarityMap, and so is inv, both computed from the parts. It acts on primitives and feature frames in its class (the class table of the Transforms guide); to_homogeneous is [s·R t; 0 1].

Plain numbers only. No consumer holds a physical similarity, so a quantity translation or scale (or a unitful EuclideanMap converted or composed with one) is refused with an ArgumentError naming the fix: strip it in metres first, ustrip(m, t) or ustrip(m, E). check = true checks the rotation and that s is positive and finite.

The trailing Src/Dst parameters are coordinate-Frame tags, as for EuclideanMap: constructors that state none give UnlabeledFrame{N}, inv swaps them, ∘ checks a labeled junction (MethodError on a mismatch), relabel/unlabel are the escape hatches.

VisualGeometryToolkitCore.RotationMap — Type
RotationMap{N, T, R <: Rotation{N, T}, Src <: Frame{N}, Dst <: Frame{N}} <: AbstractMatrixMap

A rotation about the origin, x ↦ R·x, in N dimensions, carrying the frame tags an EuclideanMap carries: it consumes Src-coordinates and produces Dst-coordinates. Its one field is the rotation R, so it has no translation at all, rather than a zero one: it poses a camera that turns about its centre (OrientedCamera), and it holds no length, so it is the same map plain and physical (has_units is false).

  • RotationMap(R::Rotation{N}; check = true), unlabeled. A RotMatrix, a QuatRotation or an Angle2d is stored as given, any other Rotation as a RotMatrix of its own eltype, by EuclideanMap's rule. RotationMap(R::StaticMatrix{N, N}; check = true) takes a raw matrix as a RotMatrix. check verifies R·Rᵀ = I, det R = 1.
  • relabel(Src, Dst, M) and unlabel(M) set and erase the tags.
  • M(x) is R·x, for a vector or a point, plain or physical.
  • inv(M) is the inverse rotation with the tags swapped.
  • A ∘ B checks the junction (B's Dst meets A's Src, the unlabeled frame a wildcard). Two rotations compose to a RotationMap. A rotation and an EuclideanMap, in either order, compose to an EuclideanMap: R_A·(R_B·x + t_B) = (R_A R_B)·x + R_A t_B and R_A R_B·x + t_A.
  • rotation(M) is R. transform_deriv(M, x) is R. to_homogeneous(M) is the (N + 1) × (N + 1) block [R 0; 0 1]. convert_eltype(T, M) rebuilds the rotation in T and keeps the tags.
  • == compares the rotations as matrices and the tags. isapprox compares the rotations' matrices, and the tags must be equal.

It is isbits, so it is a device value as it is. A persisted rotation is a Hamilton quaternion, as for poses (the stack's persisted-geometry convention); no kind writes a RotationMap yet.

using Rotations: RotY
Rk = relabel(CameraFrame, WorldFrame, RotationMap(RotY(0.3)))   # a frame's orientation: camera → world
camera = PosedCamera(model, Rk)            # an OrientedCamera; stores the extrinsics inv(Rk)
pose(camera) == Rk

VisualGeometryToolkitCore.HomographyMap — Type
HomographyMap{N,T,M<:StaticMatrix{N,N,T},Src<:Frame,Dst<:Frame} <: Transformation

Projective transformation with cached inverse for efficient covariant (points) and contravariant (lines, conics) transformations.

A HomographyMap is ALWAYS projective in meaning, whatever its matrix: a circle or an ellipse maps to a Conic. The sub-projective classes are their own maps, acting in their class (the class table of the Transforms guide, "Maps Carry the Transform Class").

Type Parameters

  • N: Matrix dimension (3 for 2D projective, 4 for 3D projective)
  • T: Element type
  • M: Matrix type — a HomographyMat (a lifted homography matrix) or a plain SMatrix (every other lift and every mixed composition)
  • Src/Dst: coordinate-Frame tags of the point FRAMES the map connects — Frame{N-1}, since the N×N matrix acts on (N-1)-dimensional frames (a 3×3 homography is 2D↔2D projective: Frame{2} on both sides). Same design as EuclideanMap: the map consumes Src-frame coordinates and produces Dst-frame coordinates (Drake monogram H_AB ≙ Src = B, Dst = A), every frame-free constructor defaults both tags to UnlabeledFrame{N-1}, inv swaps the tags, and ∘ checks a labeled junction (identical wildcard truth table — see Base.:∘ below).

HomographyMat stays frame-FREE algebra; frames are declared at the Mat → Map lift:

H = HomographyMap{TargetPlaneFrame, PixelFrame{:colmap}}(H_mat)   # labeled lift
H = HomographyMap(H_mat)                                    # unlabeled lift

relabel/unlabel are the same explicit escape hatches as for EuclideanMap.

Transformation Rules (Hartley & Zisserman conventions)

  • Points (covariant): p' = H·p
  • Lines (contravariant): l' = H^{-T}·l
  • Conics (contravariant): Q' = H^{-T}·Q·H^{-1}

Dimension Convention

  • N×N matrix operates on (N-1)-dimensional Euclidean space
  • Point{N-1} → Euclidean input, lifted via to_affine
  • Point{N} → Homogeneous input, used directly

Examples

# Lift a homography matrix, or any structured map (its analytic inverse is stored)
h = HomographyMap(HomographyMat(camera))
h = HomographyMap(EuclideanMap(RotMatrix{2}(θ), t))
h = HomographyMap(AffineMap(A, b))

# Transform points (Euclidean → homogeneous output)
p′ = h(Point2(100, 200))  # → Point3 (homogeneous)

# Transform points (homogeneous → homogeneous output)
p′ = h(Point3(100, 200, 1))  # → Point3

# Transform conics: always a Conic (classify it, or apply the structured map itself)
h(circle)   # Conic
h(ellipse)  # Conic

# Transform lines
l′ = h(Line2D(1.0, -1.0, 0.0))  # → Line2D

# Composition
h_composed = h1 ∘ h2

# Inverse is O(1) - just swaps stored matrices
h_inv = inv(h)

VisualGeometryToolkitCore.HomographyMap — Method
(h::HomographyMap{3})(c::Circle) -> Conic

Transform a circle through a homography map: a Conic, whatever the map's matrix (a HomographyMap is projective in meaning). An EuclideanMap, a SimilarityMap, a translation, rotation or uniform scaling keeps a circle a Circle, and an affine map gives a HomEllipseMat: apply them directly.

The returned conic could be:

  • An ellipse (most common for camera projections of visible circles)
  • A hyperbola (circle partially behind camera)
  • A parabola (circle tangent to plane at infinity)
  • A degenerate conic (point or lines)

Use classify_conic() to determine the conic type, then construct the appropriate geometric primitive:

H = HomographyMap(HomographyMat(camera))
circle = Circle(Point2(100.0, 100.0), 50.0)
Q′ = H(circle)  # a Conic under a camera homography

trait = classify_conic(Q′)
if trait isa EllipseTrait
    ellipse = Ellipse(Q′)  # Construct geometric primitive
elseif trait isa HyperbolaTrait
    # Handle hyperbola case
end

Example: Filter to valid ellipses

H = HomographyMap(HomographyMat(camera))
conic_matrices = H.(circles)
ellipses = [Ellipse(Q) for Q in conic_matrices if classify_conic(Q) isa EllipseTrait]

exp_so3(ω::SVector{3,T}) -> SMatrix{3,3,T,9}

Rodrigues exponential map so(3) → SO(3): R = I + a·[ω]× + b·[ω]×² with the second-order Taylor branch below the per-type small-angle threshold.

Plain SMatrix arithmetic — safe inside Zygote-tracked code (unlike RotMatrix(RotationVec(ω...)), which reverse-mode AD cannot penetrate) and generic over Real, so ForwardDiff Duals flow through it too. See also skew, left_jacobian, exp_se3.

GTSAM spells this Rot3::Expmap (and log_so3 is Rot3::Logmap), Sophus SO3::exp / SO3::log. Manifolds.jl's name is exp_lie(G, X) / log_lie: its exp(M, p, X) is the exponential at a BASE POINT, while this is the Lie-group exponential at the identity — which is why the group is not a first argument here.

VisualGeometryToolkitCore.left_jacobian — Method
left_jacobian(SO3, ω::SVector{3,T}) -> SMatrix{3,3,T,9}

Left Jacobian of SO(3): J = I + a·[ω]× + b·[ω]×² with a = (1−cosθ)/θ², b = (θ−sinθ)/θ³. Maps a rotation-vector perturbation to the translation part of the SE(3) exponential: t = J(ω)·ρ. Not provided by Rotations.jl. Below θ = 1/4, where the closed forms cancel, a and b are their six-term Taylor series (within 4 eps of the exact value); above it the closed forms.

This is Sophus' SO3::leftJacobian. GTSAM's Rot3::ExpmapDerivative is its TRANSPOSE, the RIGHT Jacobian Jr(ω) = Jl(ω)ᵀ = Jl(−ω), because GTSAM retracts by right multiplication — do not equate the two. Measured here (2026-09-22): the left perturbation identity exp(ω+δ) = exp(Jl(ω)·δ)·exp(ω) holds to 5.8e-13 while the right-multiplied one is off by 1.8e-6, and Jl(ω) = Jl(−ω)ᵀ to 0.0.

Rotation vector (axis · angle, angle ∈ [0, π]) of R — the SO(3) logarithm: the unit quaternion (w, v) of R by Shepperd's method (the largest of w, x, y, z computed from the diagonal, so every branch, the near-π one included, divides by a number ≥ ½), sign fixed to w ≥ 0, then 2·atan(‖v‖, w)·v/‖v‖ — with its Taylor series (2/w)(1 − ‖v‖²/(3w²))·v below the per-type small-angle threshold, so the derivative at the identity is exact. VisualGeometryToolkitCore.kabsch — Method
kabsch(cs) -> RotMatrix{3, T}

Kabsch/Wahba: the rotation minimizing Σᵢ ‖bᵢ − R·aᵢ‖² over the vector pairs cs (aᵢ => bᵢ, StaticVector{3} each side; any sources/targets container, a Csponds preferred): one closed-form step, Rotations.nearest_rotation of the cross-covariance Σ bᵢaᵢᵀ (an SVD with the determinant-sign correction). A weights attribute column (withattrs(cs; weights = w), data-arguments.md) weighs the pairs, Σᵢ wᵢ‖bᵢ − R·aᵢ‖² and the cross-covariance Σ wᵢbᵢaᵢᵀ (Wahba's problem): fixed, finite, non-negative weights, one per pair (an ArgumentError otherwise); a zero weight drops its pair. The vectors are used as given, NOT centred: centre them at the call site when aligning point clouds rather than directions.

Physical pairs (lengths on both sides) are stripped in metres at entry; the rotation is unit-free, so it comes back the same either way.

Throws ArgumentError on fewer than 2 pairs, or fewer than 2 of positive weight (a single pair leaves a one-parameter family of solutions).

VisualGeometryToolkitCore.mirror — Method
mirror(pose, plane_point; normal = SVector(0., 0., 1.)) -> EuclideanMap

The second branch of the planar two-fold pose ambiguity: for a PLANAR target (world-plane normal normal, any point plane_point on it — conventionally the target center), the pose whose plane normal is reflected about the viewing ray to plane_point. Under weak perspective this mirror pose predicts image positions that agree with pose to second order, so the two tie on reprojection consensus; the rotation between them is twice the viewing tilt. Total: at a frontal view the reflection is (numerically) the identity and the returned pose coincides with pose — gate on rotation_angle(RotMatrix{3}(mirror.R' * pose.R)) if the degenerate case must be skipped.

Translation is carried over unchanged (same center ray and apparent size ⇒ same depth to first order); the result is a first-order INIT for the second basin, to be refined before any comparison.

VisualGeometryToolkitCore.spectral_rotation_averaging — Method
spectral_rotation_averaging(relative) -> Dict{K, RotMatrix{3, Float64}}

Spectral chordal rotation averaging (Singer 2011; Arie-Nachimson et al. 2012): the absolute rotations of a set of frames from their relative rotations, relative an AbstractDict keyed by frame pairs (i, j) whose value R_ij takes frame i's directions into frame j's (f_j = R_ij·f_i; with d = R_k·f_k a direction in the common frame, R_i = R_j·R_ij). The 3n × 3n symmetric block matrix with blocks w_ij·R_ij at (j, i) and its transpose at (i, j), identity diagonal blocks, normalized by the frames' weighted degrees (D^{-1/2} A D^{-1/2}), has the stacked R_kᵀ in its three leading eigenvectors; each 3 × 3 block of them is projected onto SO(3) (Rotations.nearest_rotation, the eigenvectors' sign chosen so most blocks are proper), and the result is gauged so the first of the sorted frames is the identity (the common frame is that frame's). Symmetric in the frames, exact on consistent relative rotations, one eigendecomposition — the seed of a robust rotation averaging, not a robust estimator. A pair carries its non-negative weight as Attributed(R_ij, (; weight)), read with weight_of; a bare R_ij weighs 1. A zero-weight pair contributes nothing. The pairs of positive weight must connect every frame: the caller checks it on its graph (VisualGeometryToolkitEstimation's fit_rotation_averaging refuses a split one through its ViewGraph); on a split graph the leading eigenspace is degenerate and the rotations returned are meaningless (a chain with one zero-weight bridge came back 180° off).
