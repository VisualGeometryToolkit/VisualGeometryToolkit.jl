API: Experiments

The stage runner, run records, provenance and the data layer of a paper project.

Public names

VisualGeometryToolkitEval.Experiments — Module
Experiments

The paper-generic experiment-codification framework: the Stage table + run_stages entrypoint (--plan/--stage/--force), the run_driver shell-out and its in-process form run_isolated, require_input/fresher declarations, the run records (the configuration-of-record layer), the executable codification contract (contract_violations) and the one data layer of every paper project: the root ladder and artifact view (set_project_root!, data_root, ArtifactView), the input write guard (assert_not_input), the provenance record (write_provenance, read_provenance), the keyed cache (cached_result) and the data policy (data_policy_violations).

This module holds what every paper uses unchanged: the runner mechanics and the contract rules. A paper's own decisions stay in that paper's project: its stage rosters and input paths, its driver wiring (set with set_driver_context!), its artifact destinations, splits and oracle constants.

VisualGeometryToolkitEval.Experiments.RUN_CONFIG_KEYS — Constant
RUN_CONFIG_KEYS :: Vector{Pair{String,Tuple}}

Allowed keys of the run-config sections whose vocabulary THIS package defines, as dotted paths ("render.main" is the nested table). A section absent here belongs to the PROJECT that ships the config and is not key-checked — [source], [extract], [pool], [arm], [ransac] and the rest are read ad hoc by its drivers, and [source.recon_special] is keyed by scene name, so a fixed vocabulary would be wrong. [tuning.<name>] has its own, stricter check (Tuning _read_struct → VisualGeometryToolkitCore.check_keys, driven by the struct fields) and is therefore not restated here.

Nested tables are listed in their own right: a check on [render] alone sees main as one known key and nothing inside it.

VisualGeometryToolkitEval.Experiments.cached_result — Method
cached_result(f, prefix, cfg, dir; key = legacy_hash_key, force = false,
              gitpath = project_root(), ext = ".jld2", load = wload, save = nothing) -> (data, file)

The keyed result cache: <dir>/<prefix>_<key(cfg)>.jld2 is loaded (DrWatson wload) when present and its code_trees are the current ones (current_code_trees, code_tree_changes; a file without them, from before they were kept, is computed once more), else f(cfg) (a String-keyed Dict) is computed and saved tagged like DrWatson's tagsave (gitcommit + gitpatch ride along, and code_trees; uncommitted code is refused before computing, as by write_provenance) and written with DrWatson's safesave, so a forced re-run keeps the previous version as _#n. The file name is exactly the one DrWatson's produce_or_load(…; filename = hash, prefix) builds, so its existing caches are found. Justified extension: produce_or_load itself swallows save errors (DrWatson saving_files.jl:107-116 — a failed write returns the data as if cached) and forces safe = false; here a save error propagates.

Another format (a vgio record) is cached through a codec: ext names the file's extension, load(file) -> Dict reads it back and save(file, data) writes the String-keyed Dict (code trees and DrWatson's tag included); the previous version is kept as safesave keeps it (DrWatson's own recursively_clear_path: the newest previous version is <name>_#1<ext>, older ones renumbered up). A scratch_run caches as <prefix>-scratch_<key><ext>, never in a run of record's file, and its data say scratch = true.

VisualGeometryToolkitEval.Experiments.data_root — Method
data_root(; tiers = nothing, tier = nothing) -> String

The project's input tree (read-only): ENV["VGTK_DATA_ROOT"] → the project's data/exp_raw (DrWatson datadir("exp_raw"); a link, a directory, or the artifact view) → the project's fallback rung → its ArtifactView, installing tiers (default: the view's default). Configs state input paths RELATIVE to it; nothing under it is written except by a declared producer (assert_not_input).

With tier, the root of that input tier, which may live elsewhere on a machine (tier_data_root, the runner's order): ENV["<data_env>_<TIER>"] (the graph's data_env, default VGTK_DATA_ROOT) → the project's stage graph (configs/reproduce.toml, read by the runner's load_stage_graph) [sites.<site>.tiers], <site> from ENV["VGTK_SITE"] (the runner sets both for its jobs) → the one data root above, through the same resolver and the runner's view gate (catalog_view_mount): a tier the project's catalog (configs/data_artifacts.toml) lists is the view's, its root where the view mounts it (<data root>/<mount_dir>, a split entry's parts included), installed when the view's Artifacts.toml binds it; a tier the catalog does not list is only looked up. An [inputs.<id>] path is relative to its tier's root, so input_path fetches what it reads.

VisualGeometryToolkitEval.Experiments.run_complete — Method
run_complete(outdir; sidecar, gitpath = project_root()) -> Bool

Keyed skip-if-complete: a run counts as done only when its result sidecar (a file name under outdir) AND its _provenance.toml exist, and the code trees that record keeps are the current ones (code_tree_changes of the recorded code_trees and current_code_trees(gitpath)). VisualGeometryToolkitEval.Experiments.run_isolated — Method
run_isolated(path; args = String[], env = Dict{String,String}(),
             bindings = Dict{Symbol,Any}()) -> Module

Include the script path in a fresh module of its own, in this process: a paper driver defines top-level constants meant for a process of its own, so several drivers included into one session collide, while a throwaway module gives each the clean top level it expects and keeps the loaded packages warm (no new process, no recompilation). While the script's top level runs, ARGS is args and the environment holds env (both restored afterwards, also on error); bindings are constants defined in the module first (a name the script uses unqualified). The module's exit throws instead of ending the session. Returns the module: the functions the script defined live in a newer world, so call them through Base.invokelatest. A separate process (run_driver) is the other way to run a driver.

VisualGeometryToolkitEval.Experiments.run_key — Method
run_key(cfg; files = nothing, upstream = nothing, parts = nothing) -> String

The run identity: the SHA-256 (hex, first 16) of the effective config's canonical JSON (_content_key: VisualGeometryToolkitCore's canonical_json, the one content key behind tuning_hash and the runner's stage key too), with the RUN_KEY_EXCLUDED sections removed ([render] holds panel knobs of record, not experiment inputs) and every [tuning.<name>] entry resolved to its COMPLETE table (resolve_tuning!: a default of this package's configs/tuning.toml that the config inherits keys the run like a stated one). Key order does not move it, nor a number's spelling (3 and 3.0 key alike), the Julia version does not move it, and a TOML round trip of the effective config reproduces it, so run_key(TOML.parsefile("_config.toml")) names the directory that holds it.

What a run depends on beyond its config is folded in by name, so a project keys it here instead of in a private hash:

  • files: name => path, each file's content hash (file_sha256: streamed, cached by path, size and mtime) — a calibration file, a board definition;
  • upstream: name => key, the run keys of the runs it reads (a pose run's key in the key of the evaluation that reads its poses), or name => run directory, read for its recorded run_key (a scratch run's is refused);
  • parts: name => value (a Dict or a NamedTuple, TOML values), a choice of the run that is not in its config (a frame limit of a smoke run).

They are keyed as the table keyed_with (files, upstream, parts, each present when given; and scratch in a scratch_run, so its outputs never share a run of record's directory), which a config therefore may not hold; without them the key is the config's alone, as before. A value of record belongs in the config: parts is for a choice made on the command line of a driver.

VisualGeometryToolkitEval.Experiments.run_stages — Method
run_stages(experiment::AbstractString, stages; argv = ARGS)

The uniform experiment entrypoint: --plan prints the stage table and exits (the structural check); otherwise runs every pending stage in declaration order (--stage=NAME restricts to one, or to a comma-separated subset — declaration order is still honored; --force re-runs done stages). The printed table is a snapshot; each stage's done() is RE-EVALUATED immediately before it would be skipped, because an earlier stage of the same run may have invalidated it. A stage failure aborts the run (later stages depend on earlier ones).
