API: Experiments

The stage runner, run records, provenance and the data layer of a paper project.

Public names

VisualGeometryToolkitEval.Experiments — Module
Experiments

The paper-generic experiment-codification framework: the Stage table + run_stages entrypoint (--plan/--stage/--force), the run_driver shell-out and its in-process form run_isolated, require_input declarations, the keyed product (Product, produce: DrWatson's produce_or_load), the run records (the configuration-of-record layer), the executable codification contract (contract_violations) and the one data layer of every paper project: the root ladder and artifact view (set_project_root!, data_root, ArtifactView), the input write guard (assert_not_input), the provenance record (write_provenance, read_provenance) and the data policy (data_policy_violations).

This module holds what every paper uses unchanged: the runner mechanics and the contract rules. A paper's own decisions stay in that paper's project: its stage rosters and input paths, its driver wiring (set with set_driver_context!), its artifact destinations, splits and oracle constants.

VisualGeometryToolkitEval.Experiments.RUN_CONFIG_KEYS — Constant
RUN_CONFIG_KEYS :: Vector{Pair{String,Tuple}}

Allowed keys of the run-config sections whose vocabulary THIS package defines, as dotted paths ("render.main" is the nested table). A section absent here belongs to the PROJECT that ships the config and is not key-checked — [source], [extract], [pool], [arm], [ransac] and the rest are read ad hoc by its drivers, and [source.recon_special] is keyed by scene name, so a fixed vocabulary would be wrong. [tuning.<name>] has its own, stricter check (Tuning _read_struct → VisualGeometryToolkitCore.check_keys, driven by the struct fields) and is therefore not restated here.

Nested tables are listed in their own right: a check on [render] alone sees main as one known key and nothing inside it.

VisualGeometryToolkitEval.Experiments.Product — Type
Product(experiment, name, record; output, files = nothing, upstream = nothing, parts = nothing,
        code = current_code_trees(project_root()))

The keyed product of one step of a pipeline of experiment (a name, or a relative path of segments for a project whose results are laid out deeper: "ETH/sift/homography/fig4"): its name ("prepare", "start", "refine", …), the record it is keyed by (ONLY the config fields and inputs the product reads), its key and its output, the file under the product's directory (product_dir) that holds its result — the record produce saves, or the file a product that writes its own outputs writes last.

The key is THE dependency tracking of a pipeline (run_key(record; files, upstream, parts, code)): the record (a top-level section that a run key excludes, RUN_KEY_EXCLUDED's render, is refused in it: it would key nothing; a product that reads it keys it under another name); the products it reads (upstream: a Product, whose key AND its output's content hash, recorded when it was produced, are folded in — so an upstream produced again with another output re-keys this one, and produced checks it again; or a bare key, folded as it is: no output hash, so a bare key is not re-keyed when its product is produced again — give the Product); the content of the files it reads (files; a config's pinned inputs belong in its record, by their sha256); a choice made on a command line (parts); and the CODE it runs (code): the source-tree hash of every stack package its environment loads and the project's own src (current_code_trees: a path checkout's git trees of src, ext, Project.toml, a registered version's Manifest tree hash). A change of any of them is another key, so another directory, produced anew; an unchanged one is the same product, loaded. A change of a package re-keys every product that loads it (conservative). A product whose computation runs only some of the environment's packages is keyed by those alone — the per-package rule: code restricted to the packages its step uses (a step that runs an external tool adds the tool's pinned image to its inputs), never a driver's own source — so a commit elsewhere leaves it produced. A result of an earlier key stays where it is.

VisualGeometryToolkitEval.Experiments.Stage — Type
Stage(name::Symbol, desc::String; items, product, run)
Stage(name::Symbol, desc::String; check)

One stage of a codified experiment. A stage that PRODUCES declares its items (items(): the cases, sets or names it treats — cheap: no GPU, no heavy loads), each item's keyed product (product(item), an experiment's Product) and its runner (run(item), which calls produce: a produced product loads, a pending one is produced through DrWatson's produce_or_load), so run is called for every item of the stage and a stage whose products are all produced costs their checks only. A stage that only CHECKS (its inputs present, a refusal, a deploy) declares check(), run every time. Declared in figure/table order and executed by run_stages.

The done-closure form Stage(name, desc, done, run) is retired: a product's own record says whether it is produced.

VisualGeometryToolkitEval.Experiments.data_policy_violations — Method
data_policy_violations(root; dirs = ["src", "scripts"], exts = [".jl", ".sh", ".sbatch"],
                       allow = DataPolicyAllow[])
    -> Vector{NamedTuple{(:rule, :file, :line, :text)}}

The data-policy findings (rules D1–D5, see the file header) in the dirs of project root (code, the exts files: every rule, comments skipped; their other text files: D1), and D1 also in its tests, examples, configs, docs and provenance (every line of their code, config and text files; a site profile, which holds a machine's paths by design, excepted) and in every Markdown file of the root and of data/ (README.md, REPRODUCE.md, data/README.md, …). VisualGeometryToolkitEval.Experiments.data_root — Method
data_root(; tiers = nothing, tier = nothing) -> String

The project's input tree (read-only): ENV["VGTK_DATA_ROOT"] → the project's data/exp_raw (DrWatson datadir("exp_raw"); a link, a directory, or the artifact view) → the stage graph's [sites.<site>] data_root once it exists → the site profile's data_root once it exists (active_site, its {project} the project_name) → the project's fallback rung → its ArtifactView, installing tiers (default: the view's default). Configs state input paths RELATIVE to it; nothing under it is written except by a declared producer (assert_not_input).

With tier, the root of that input tier, which may live elsewhere on a machine (tier_data_root, the runner's order): ENV["<data_env>_<TIER>"] (the graph's data_env, default VGTK_DATA_ROOT) → the project's stage graph (configs/reproduce.toml, read by the runner's load_stage_graph) [sites.<site>.tiers], <site> from ENV["VGTK_SITE"] (the runner sets both for its jobs) → the one data root above, through the same resolver and the runner's view gate (catalog_view_mount): a tier the project's catalog (configs/data_artifacts.toml) lists is the view's, its root where the view mounts it (<data root>/<mount_dir>, a split entry's parts included), installed when the view's Artifacts.toml binds it; a tier the catalog does not list is only looked up. An [inputs.<id>] path is relative to its tier's root, so input_path fetches what it reads.

VisualGeometryToolkitEval.Experiments.input_path — Method
input_path(cfg, id; root = nothing) -> String

The absolute path of the config's input [inputs.<id>]: its path under its tier's root (data_root(; tier): VGTK_DATA_ROOT_<TIER>, the stage graph's [sites.<site>.tiers], the results root for a tier the catalog mounts there (mount = "results": a run of record published as a tier), the data root), or under root when given; checked to be there and, with a sha256, to have that content (streamed, cached). The one reader a driver opens an input with; an ArgumentError for an id the config does not declare, a missing input or another content.

An input may instead name ANOTHER project's keyed product — its run of record, read where it lives, never copied:

[inputs.hand_eye]
project = "bmvc2026"                    # the producing project (its stage graph's [project] name)
product = "calibration/hand_eye"        # the Product's <experiment>/<name>
key = "3f9a0c1d2e4b5a67"                # its run key of record (the product's directory)
file = "hand_eye_bb.json"               # optional: a file in the product's directory (default: the directory)
sha256 = "…"                            # its content (a directory's: tree_sha256)
tier = "bmvc2026_results"               # optional: a results-mount tier of this project's catalog publishing them

It is read under the first root that holds <product>/<key>[/<file>]: VGTK_RESULTS_ROOT_<PROJECT>, then project_results_root (the active site profile's results_root for that project), then the tier's root (the fresh-machine form: the producer's results published as a tier, fetched by DataArtifacts); its record's run_key must be key (VisualGeometryToolkitEval's product_input, the runner's check too). With root, that root alone is the product's results root.

VisualGeometryToolkitEval.Experiments.produce — Method
produce(f, s::Product; driver, config_source, inputs = String[], producer = false, fields = Dict(),
        force = false, gitpath = project_root()) -> String

The product s reused or produced — produced through DrWatson's produce_or_load on the product's output (loadfile = false). VisualGeometryToolkitEval.Experiments.run_isolated — Method
run_isolated(path; args = String[], env = Dict{String,String}(),
             bindings = Dict{Symbol,Any}()) -> Module

Include the script path in a fresh module of its own, in this process: a paper driver defines top-level constants meant for a process of its own, so several drivers included into one session collide, while a throwaway module gives each the clean top level it expects and keeps the loaded packages warm (no new process, no recompilation). While the script's top level runs, ARGS is args and the environment holds env (both restored afterwards, also on error); bindings are constants defined in the module first (a name the script uses unqualified). The module's exit throws instead of ending the session. Returns the module: the functions the script defined live in a newer world, so call them through Base.invokelatest. A separate process (run_driver) is the other way to run a driver.

VisualGeometryToolkitEval.Experiments.run_key — Method
run_key(cfg; files = nothing, upstream = nothing, parts = nothing) -> String

The run identity: the SHA-256 (hex, first 16) of the effective config's canonical JSON (_content_key: VisualGeometryToolkitCore's canonical_json, the one content key behind tuning_hash and the runner's stage key too), with the RUN_KEY_EXCLUDED sections removed ([render] holds panel knobs of record, not experiment inputs) and every [tuning.<name>] entry resolved to its COMPLETE table (resolve_tuning!: a default of this package's configs/tuning.toml that the config inherits keys the run like a stated one). Key order does not move it, nor a number's spelling (3 and 3.0 key alike, as do TOML's hex 0x0b10b5eed and 2970312429), the Julia version does not move it, and a TOML round trip of the effective config reproduces it, so run_key(TOML.parsefile("_config.toml")) names the directory that holds it.

What a run depends on beyond its config is folded in by name, so a project keys it here instead of in a private hash:

  • files: name => path, each file's content hash (file_sha256: streamed, cached by path and stat) — a calibration file, a board definition;
  • upstream: name => key, the run keys of the runs it reads (a pose run's key in the key of the evaluation that reads its poses), or name => run directory, read for its recorded run_key (a scratch run's is refused);
  • parts: name => value (a Dict or a NamedTuple, TOML values), a choice of the run that is not in its config (a frame limit of a smoke run);
  • code: package => tree, the code version of what the run loads (current_code_trees: a path checkout's git trees, a registered version's Manifest tree hash) — a Product's key always folds it.

They are keyed as the table keyed_with (files, upstream, parts, code, each present when given; and scratch in a scratch_run, so its outputs never share a run of record's directory), which a config therefore may not hold; without them the key is the config's alone, as before. A value of record belongs in the config: parts is for a choice made on the command line of a driver.

VisualGeometryToolkitEval.Experiments.run_stages — Method
run_stages(experiment::AbstractString, stages; argv = ARGS)

The uniform experiment entrypoint: --plan prints the stage table (each stage's produced products of its items, or check) and exits (the structural check); otherwise runs the stages in declaration order (--stage=NAME restricts to one, or to a comma-separated subset — declaration order is still honored). A producing stage calls its run on EVERY one of its items, which loads a produced product and produces a pending one; its items are listed when the stage runs, so a product an earlier stage re-keyed is the new one. --force unmarks each product of the selected stages (its provenance removed) just before its item runs, so each is produced again and a failure leaves the later ones as they were. A stage failure aborts the run (later stages depend on earlier ones).
