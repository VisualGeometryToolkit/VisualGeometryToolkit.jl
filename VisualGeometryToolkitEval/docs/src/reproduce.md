# Reproducible figures

Every figure, table and number macro in a camera-ready paper is generated by
tracked code from declared data. Each one is listed in the paper project's
`REPRODUCE.md`, and a test enforces the list. A hand-made asset is allowed only
when it is declared `static` and carries a provenance note.

## The asset index

The index is a Markdown table. It has at least the columns `asset`, `kind` and
`generator`; the columns `label`, `config`, `data` and `provenance` are read
when present. Cells hold their values in backticks. Paths are relative to the
project directory, and an asset may be a glob: `*` matches within a path
segment and `**` across segments.

```markdown
| label | asset | kind | generator | config | data | provenance |
|---|---|---|---|---|---|---|
| `fig:teaser` | `papers/images/intro_overlay.png` | generated | `scripts/make_intro.jl` | `configs/figures/intro.toml` | images tier | |
| — | `papers/figures/stats.tex` | generated | `scripts/make_stats.jl` | `configs/figures/stats.toml` | promoted run | |
| `fig:arch` | `papers/images/architecture.pdf` | static | — | — | — | drawn in Inkscape by the authors from the network definition, 2026-05 |
```

## Generators and their configs

A generator *writes* its asset when it names the file, or when it declares it
in a comment line `reproduce: writes <path-or-glob>`. It *reads* its config of
record when it names the file, or when it declares `reproduce: reads <path>`.
Both paths are relative to the project, and any comment syntax works.

Every parameter of a generator belongs in its config of record, not in the
script. That covers frame picks, crops, seeds, panel lists, sizes and inputs.

## The enforcing test

The project's suite holds the contract:

```julia
using Test
using VisualGeometryToolkitEval.Reproduce: reproduce_index_violations

vs = reproduce_index_violations(project_dir; papers = ["papers/main.tex", "papers/supp.tex"],
                                require_config = true)
foreach(println, vs)
@test isempty(vs)
```

[`reproduce_index_violations`](@ref) reports each of these:

- an asset the paper reads that no entry covers;
- a missing asset;
- a reference whose path is not static;
- a stale entry;
- an unknown kind;
- a generated entry without an existing generator;
- a generator that does not write its asset;
- a generated entry without a config of record (with `require_config`);
- a missing config, or one that its generator does not read;
- a static entry without provenance;
- an entry filed under the label of another float;
- a number defined by a generated macro file and re-typed as a literal in the
  prose. This check is best effort. A coincidence is exempted with
  `% reproduce: literal-ok` on its line.

A paper built outside its own directory — a `main.tex` in `paper/src/`
compiled from `paper/` that writes `\input{src/sec/intro}` — resolves its
references through `search_dirs` (project-relative), the build's compile
directory and TEXINPUTS: `reproduce_index_violations(dir; papers, search_dirs =
["paper"])`, or `paper_project_violations(dir; papers, reproduce = (; search_dirs
= ["paper"]))`.

## Verify, deploy and the numbers file

A generator renders into its results, never into the paper. The last stages of
a regeneration compare each render with the submitted copy and replace a
submitted asset only with the author's sign-off:

```julia
using VisualGeometryToolkitEval.Reproduce

verify_assets(outdir, paperdir, names)          # writes outdir/verify.tsv, prints each verdict
deploy_assets(outdir, paperdir, names;          # verifies first; a differing submitted copy is
              replace_submitted = false)        # refused unless signed off
```

A `.tex` asset is compared by its numbers as well as its bytes
([`compare_fragments`](@ref): its pgfplots `coordinates` and its macros), so a
reformatted fragment reports "same numbers". The numbers file is one more asset
under the same rule: [`gather_numbers`](@ref) writes it beside the generator's
results from the drivers' fragments, one `\newcommand` per number, and
`deploy_assets` puts it into the paper. [`uncited_macros`](@ref) lists the
numbers the paper defines but never cites, over the files the paper reads
(the ones [`paper_asset_graph`](@ref) visits), with an allow table of reasons.

## Writing a driver's numbers

Every number a performance change could move is a macro: a number of the
prose, each cell of a table row, a value a figure (its caption, its axis)
reads. A driver writes its numbers with the one writer, into a fragment beside
its results; [`gather_numbers`](@ref) gathers the fragments into the numbers
file, and [`deploy_assets`](@ref) puts that into the paper only once the
author has signed off a change (`replace_submitted`).

```julia
using VisualGeometryToolkitEval.Reproduce
using VisualGeometryToolkitEval.Experiments: read_provenance

nums = PaperNumbers(; driver = "scripts/hand_eye.jl", config = "configs/hand_eye.toml",
                    run_key = KEY, commit = read_provenance(OUTDIR)["gitcommit"])   # the run's commit
add_number!(nums, "heFrames", 240)                                  # a number of the prose
add_number!(nums, number_macro_name("he", "rot_deg", "p90"), 0.0412; digits = 3)
add_number!(nums, "heShare", 0.256; percent = true, digits = 0)     # 26\%
add_number!(nums, "teaserBoards", 12; label = "fig:teaser")         # a value a figure reads
row = add_table_row!(nums, "heBaxter", ["frames" => 61, "transMm" => tex_number(1.234; digits = 2)];
                     label = "tab:handeye")                         # "\heBaxterFrames & \heBaxterTransMm"
write_numbers(joinpath(OUTDIR, "numbers.tex"), nums)
```

The fragment holds, sorted by name, each macro after its provenance comment:

```latex
% provenance \heBaxterFrames: driver=scripts/hand_eye.jl; config=configs/hand_eye.toml; run=3f2a9c1e; commit=f11598f7; label=tab:handeye
\newcommand{\heBaxterFrames}{61}
```

- **Format** ([`tex_number`](@ref)): `digits` fixed decimals (Printf's
  `%.<d>f`), or `sigdigits` significant digits without trailing zeros and
  without an exponent; an integer needs neither. `percent`, `group_from`
  (thin-space thousands), `unit`, and a range `(lo, hi)` with its
  `range_separator`. A NaN or an infinity is refused: a missing evaluation
  fails the stage. A string value is a body already typeset (`"---"`,
  `"10^{-6}"`), one value with balanced braces.
- **Names** ([`number_macro_name`](@ref)): letters only, never beginning with
  `end`; a driver prefix and name parts, each digit spelled out
  (`"fx3_14mm"` → `FxThreeOneFourMm`).
- **A table row is one macro per cell.** The table's tex reads the row
  [`add_table_row!`](@ref) returns, and the prose cites a cell by the same
  macro. One macro holding `a & b & c` would hide its numbers from
  [`compare_fragments`](@ref), [`macro_literal_violations`](@ref) and
  [`uncited_macros`](@ref), which read a macro's value as one number.
- **Provenance**: the driver, its config of record (project-relative), the run
  key and the run's commit (its recorded `gitcommit`: the comment changes only
  when the run does). A number read from another run overrides fields with
  `provenance = (; run_key = …)`. [`gather_numbers`](@ref) keeps each comment,
  and [`deploy_assets`](@ref) deploys a numbers file that differs from the
  submitted one in its `% provenance` lines alone (a rerun at a new run key or
  commit; the verify report's `provenance_only`) without sign-off. Any other
  change, a value, a hand-written comment or whitespace, still needs it.
- **Deterministic**: the same numbers write the same bytes, whatever the
  order they were added in; the fragment is written whole (a temporary file
  renamed into place).
- **Direction** (`better`): `:lower` (an error, a time), `:higher` (a rate,
  a score) or `:none` (a count, a setting), recorded in the provenance comment
  (`; better=lower`). A results branch's comparison calls a change of the
  number IMPROVED or DEGRADED by it; a number without one is CHANGED, with no
  verdict. [`add_table_row!`](@ref) takes one direction for the row or
  `column => direction` pairs.

## Results branches: a full reproduction under review

A full reproduction with updated code becomes a branch of the paper's
repository, examined before anything reaches the paper:

```julia
using VisualGeometryToolkitEval.Reproduce

run = results_branch(projectdir(), [render => "paper/src/fig/teaser.png", numbers => "paper/src/latex/numbers.tex"];
                     run_keys, tiers = ["rc_baselines" => tier_dir], slurm_jobs, gpus, wall_times)
# run.branch == "results/20261111_021530-3de1a4f": the UTC stamp and the evaluated commit
accept_results(projectdir(), run.branch; replace_submitted = true)   # one merge commit, tag accepted/20261111_021530
remove_results_worktree(projectdir(), run.branch)                    # after acceptance, or as the rejection
```

- [`results_branch`](@ref) creates the branch from the base (the checked-out
  branch) in a worktree of its own under the scratch root
  (`VGTK_RESULTS_WORKTREES`, else `<repository>-results` beside the
  repository); the user's checkout is not touched. Its one commit holds the
  renders at the paper's paths (macros, tables, figures: nothing large),
  `RUN.toml` (the code commit, each data tier's hash, the run keys under which
  the heavy results stay in the results root, the machine, GPUs (detected by
  nvidia-smi or CUDA.jl when not given), Slurm jobs and wall times; a run that
  gives no tiers, GPUs or wall times is warned about and `missing` names them)
  and `COMPARISON.md`: every macro's base and new value, its delta and its
  verdict (a changed unit or percent sign is CHANGED), every asset's verify
  verdict, each changed PNG beside the base's copy. A failure after the
  worktree is created removes the worktree and the branch.
- [`accept_results`](@ref) is never automatic. It deploys the branch's assets
  into the base through [`deploy_assets`](@ref) (a changed asset needs
  `replace_submitted`), as one merge commit made in a worktree of its own, then
  tags it `accepted/<stamp>`, then moves the base to it: a checkout of the base
  fast-forwards (refused when an accepted asset has local changes: the tag is
  deleted again and the base stays), a checkout on another branch is
  untouched. A base that moved since the run is a warning naming the accepted
  assets it changed. The manifest and the comparison stay on the branch.
- [`remove_results_worktree`](@ref) removes the worktree and keeps the branch,
  or deletes it with `delete_branch = true`.

A driver defines top-level constants meant for a process of its own;
[`run_isolated`](@ref) includes it in a module of its own, so one regeneration
script can run every driver in one warm session.

`src/reproduce/reproduce_index.jl`, `src/reproduce/number_macros.jl` and
`src/reproduce/paper_assets.jl` depend on Base only, so an environment that
cannot load this package can include them by path, in that order
(`src/reproduce/results_branches.jl` is not among them: it runs git and reads
TOML).
