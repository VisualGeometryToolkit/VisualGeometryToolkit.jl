Quantities, Frames and Detections

VisualGeometryToolkitIO owns the stack's quantity JSON format. A quantity in a JSON record is a number in the unit the record declares, and the record declares its units once, inline: "units": {"world": "mm", "density": "dpi"}, a UnitContract (with further length roles where one record needs more than one length unit, below). A length is a number in the world unit, a density (pixels per length) a number in the density unit, and a pixel count a number of pixels. The unit is not repeated beside every value.

What a number is — a length, a pixel count or a density — is the record's to say, field by field, because a pixel is dimensionless and a number alone cannot tell a pixel count from an angle or a ratio. write_quantity and read_quantity convert one quantity:

julia> using VisualGeometryToolkitCore, VisualGeometryToolkitIO

julia> import JSON

julia> import VisualGeometryToolkitIO as VgtkIO

julia> VgtkIO.write_quantity(62.8mm, MM_PX), VgtkIO.write_quantity(640px, MM_PX), VgtkIO.write_quantity(300dpi, MM_PX)
(62.8, 640, 300)

julia> VgtkIO.read_quantity(0.0628, :length, UnitContract(world = m)) == 62.8mm
true

julia> VgtkIO.json_value(MM_PX)   # the record's declaration
(world = "mm", density = "dpi")

A length crosses through read_length and write_length, so a millimetre number reads and writes back to its own text. A pixel count and a density are written as integers when they are integral. A quantity of any other dimension has no declared unit and is an ArgumentError.

Sizes, feature frames and detections

json_value(x, contract; kind) is the plain value a record holds for one of VisualGeometryToolkitCore's values, which JSON.json writes, and from_json(T, d, contract; kind) reads it back from a parsed object. These are explicit functions, not methods of JSON.jl's lower and lift.

ValueJSON object
Size2{"width": w, "height": h}
Disc{"center": [x, y], "σ": s}
OrientedDisc{"center": [x, y], "σ": s, "θ": angle}
EllipticFrame{"center": [x, y], "S": [S11, S21, S12, S22]}
AffineFrame{"center": [x, y], "A": [A11, A21, A12, A22]}

Matrices are written as their four entries in column order. A Size2 or a Disc holds plain numbers or quantities of ONE kind, and both its writer and its reader declare which with the required keyword kind (:plain, :length or :pixel); there is no default, because a default would hand a length or a pixel count back as a bare number. The other frames hold plain numbers (kind = :plain).

julia> s = JSON.json(VgtkIO.json_value(Size2(width = 210.0mm, height = 297.0mm), MM_PX; kind = :length))
"{\"width\":210.0,\"height\":297.0}"

julia> VgtkIO.from_json(Size2, JSON.parse(s), MM_PX; kind = :length) == Size2(width = 210.0mm, height = 297.0mm)
true

A detection — an Attributed feature frame, VisualGeometryToolkitCore's AbstractDetection, which VisualGeometryToolkitFeatures' Detection is — is one JSON object. Its frame is under frame, and every metadata field is under its own name; the frame's type is read off its keys. A detection with an Uncertain frame (from uncertainty = FeatureCovariance()) also has cov, the covariance's entries in column order, or null when the covariance is not finite (a keypoint the detector could not refine), written with the matrix's size N under cov_size; reading it back makes the frame Uncertain again, with the same N×N covariance. The size is the value's, not the frame's: an ASIFT EllipticFrame carries a 3×3 covariance over (x, y, log σ). A null without cov_size (IO v0.1.0's record) reads as 3×3, as v0.1.0 read it, and cov_size is not a metadata name. On reading, the documented metadata fields (response, edge_score, laplacian_scale_score) come first and as Float64, and the other fields follow, sorted by name, as they were parsed. Metadata has no declared kind, so a quantity in it is refused on writing.

julia> d = Attributed(Disc(Point2(10.5, 20.25), 3.0), (response = 0.25, laplacian_scale_score = 1.0));

julia> s = JSON.json(VgtkIO.json_value(d, MM_PX; kind = :plain))
"{\"frame\":{\"center\":[10.5,20.25],\"σ\":3.0},\"response\":0.25,\"laplacian_scale_score\":1.0}"

julia> VgtkIO.from_json(AbstractDetection, JSON.parse(s), MM_PX; kind = :plain) == d
true

With VisualGeometryToolkitFeatures loaded, from_json(Detection, obj, contract; kind) reads the same object.

Length roles: more than one length unit in one record

A record whose lengths are declared in more than one unit — a board's canvas in millimetres and its pattern in points — names each further unit as a LENGTH ROLE of its contract: UnitContract(world = mm, lengths = (pattern = pt,)), declared "units": {"world": "mm", "density": "dpi", "lengths": {"pattern": "pt"}}. In memory the contract is the table of its roles, with world an ordinary, required entry of it (c.lengths == (world = mm, pattern = pt); role_unit(c, role) reads one and lists the declared roles when asked for another); only the serialiser knows the file layout above, world at the top level and the other roles under "lengths". A length field read or written in a role names it (role = :pattern; :world is the default), so each number is decimal-exact in its own unit: a point value has no exact millimetre decimal.

julia> c = UnitContract(world = mm, lengths = (pattern = pt,));

julia> q = VgtkIO.read_length(2.12598425197, pt);

julia> VgtkIO.write_quantity(q, c; role = :pattern), VgtkIO.read_quantity(2.12598425197, :length, c; role = :pattern) === q
(2.12598425197, true)

julia> VgtkIO.json_value(c)
(world = "mm", density = "dpi", lengths = (pattern = "pt",))

One quantity form

The {"value": v, "unit": u} object that VisualGeometryToolkitFeatures' JSON.jl hooks once wrote, and that BlobBoards' board files hold, is not read: read_quantity and every from_json refuse it, naming the migration. A file that holds it is migrated once by its owner (vgio_migrate, extended for the owner's schema through migrate_schema).

ScalarOrQuantity is the type of a field that may hold a plain number or a quantity.
